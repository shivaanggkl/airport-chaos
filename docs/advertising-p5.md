## Delivery and rendering

- The existing `GET /api/sponsorship/catalog` adds a bounded `world` array. The server uses P3 campaign preview, approved creative integrity, advertiser/campaign review, UTC half-open schedule, delivery approval, assignment city and exact P1 placement whitelist. Hub and world flags are independent; global pause overrides both. A conflict fails closed for that placement. The public catalog contains only city/placement/campaign/creative IDs and a hash-versioned same-origin asset URL; it excludes private advertiser and inquiry data. The existing creative route serves a world asset only while its creative remains catalog-eligible.
- Production remains hard-disabled. Isolated local QA required nonproduction Node, loopback, explicit `AIRPORT_CHAOS_DEV_QA=1`, `SPONSORSHIP_QA_SERVING_ENABLED=true`, `SPONSORSHIP_PAID_WORLD_ENABLED=true`, `SPONSORSHIP_GLOBAL_PAUSE=false`, and temporary SQLite/asset paths. P3 approval alone and the Hub gate alone did not serve a world creative. No client parameter can change these server controls.
- The Three.js adapter changes the material on each existing near/mid/far sign panel; it creates no placement geometry. It validates loaded image aspect against the sign (8% tolerance), reuses one texture/material across a sign's LOD panels, and restores retained house materials on failure, removal, expiry, or city unload. Pending loads are token-guarded. City entry/foreground refresh uses the P4 catalog with a one-shot validity timer (at most 60 seconds); no requests occur in the frame loop. The original house art appears immediately and flight never waits for a catalog.
- The existing local visual QA preset needed one narrow correction: deterministic camera/route inspection no longer sends artificial aircraft transforms to the authoritative server or triggers flight rewards. This resolved the repeated reconnects seen during QA. It is loopback-only; normal movement and server validation remain unchanged.
