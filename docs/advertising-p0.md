## Reward economy and trust boundary

`shared/rewarded-ads.mjs` remains authoritative for **50, 75, 100, 150 Credits** (375 total), at most four verified rewards per Daily Reward claim, a **one-hour** claim window, and a separate **30-minute** attempt lifetime. Daily Reward cooldown and wallet calculations are unchanged. The client renders step values from server status; web never registers a native provider. Native development uses test units by default; production `AIRPORT_CHAOS_REWARDED_ADS_ENABLED` defaults false and real production ad-unit configuration is absent from the repository.

The server owns attempt creation, step selection, and wallet crediting. It requires a player session and native platform for player-facing ad endpoints, same-origin JSON for mutations, and pilot/IP rate limits. Google SSV signatures are verified against Google's public keys; ad unit, reward item/amount, attempt ID, transaction ID, timestamp, and Daily Reward claim are checked. SQLite statements use parameters; wallet grant, provider transaction, and attempt completion share one transaction, with unique provider transaction IDs and wallet idempotency keys. Closed, failed, expired, mismatched, duplicated, or unverified client events cannot grant Credits. Pending attempts survive server restart in SQLite. A late network callback for an in-window completion is allowed; completion after the one-hour boundary is rejected. No client message supplies reward amount or changes Sky Tokens.

No sponsor creation/assignment endpoints, advertiser script execution, sponsor click redirect, sponsor identity export, or client-authoritative impression billing were found. Static contact links are first-party email/website values. Future advertiser text, links, and creative will require server-controlled approval, URL allowlisting, text encoding, authorization, rate limits, and identity-safe reporting in P3–P6.
