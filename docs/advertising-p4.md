# Advertising P4 — Hub sponsorship and sponsor safety

**Engineering status:** P4 engineering verification complete, including a controlled P4-off versus P4 Hub performance comparison. This is an isolation test, not a recovered historical P3 build. Commercial serving, external sponsor links, and public inquiry collection remain off. This phase did not implement P5 world delivery.

## Source and implementation

- Worktree: `feature/advertising` at `95a6787e9b37de3f7a50922660f3004ee71ec957`, with P0–P4 uncommitted. The separate `qa` worktree at `airport-chaos-sky-duel` was not modified. The P1 inventory remains 102 authored + 48 generated, with the same three QA-approved Dallas signs. P4 does not alter Dallas rendering, missions, Sky Duel, wallets, purchases, or native ad SDKs.
- `server/src/sponsorship-management.ts` extends the existing SQLite entities with default-off, auditable `directory_approved` and `delivery_approved` fields and a reviewed public description. The migration is repeatable. Material campaign edits, assignment changes, pauses, cancellations, or advertiser suspension invalidate or remove public eligibility. Approved creative content remains hash-checked against the registered local file. The same P3 schedule preview and conflict rules drive delivery; no client chooses a sponsor.
- `server/src/sponsorship-delivery.ts` resolves the single Hub slot. `GET /api/sponsorship/catalog` returns only public fields, a revision, validity boundary, and at most one Hub sponsor. It returns house/empty data on missing approval, conflict, invalid creative, unsupported platform, pause, or release-gate failure. The creative endpoint only serves the currently eligible, hash-matching same-origin image. No public management API exists. The directory currently derives only from an approved Hub campaign; future P5 world inclusion must use the same server service and separate world gates.
- Production delivery is hard-disabled in P4. Local QA requires nonproduction Node, no Render service, `AIRPORT_CHAOS_DEV_QA=1`, a database and asset root both under the system temp directory, `SPONSORSHIP_QA_SERVING_ENABLED=true`, `SPONSORSHIP_PAID_HUB_ENABLED=true`, `SPONSORSHIP_GLOBAL_PAUSE=false`, and a loopback request. These are server-owned controls. `SPONSORSHIP_EXTERNAL_LINKS_ENABLED` is separately default-off and was not enabled in browser QA. No query parameter, local storage value, P3 approval, or player action turns on serving. A production rollout still requires a new approved release implementation and the P0 audience/privacy/legal gates.
- The existing Hub banner renders house immediately, then validates the catalog asynchronously. The sponsored state uses the approved local image, public name/tagline, and visible `SPONSORED` label in the original footprint. The single bounded expiry timer clears paid content at the server validity limit (at most 60 seconds, earlier at campaign end); returning to Hub or foreground revalidates. No flight-frame work, polling loop, WebSocket subscription, or 3D asset was added.
- `/sponsors` displays only currently eligible, explicitly listed advertisers; direct `/sponsors/<advertiser-id>` opens Sponsor Details without player sign-in. Hub selection opens details before any external action. The website action is absent while gated; when a future authorized QA configuration permits it, only the operator-approved HTTPS URL is used with `noopener noreferrer` and no player identifier. Back/Escape and focus return were checked in the real Hub. The empty directory and house banner retain the existing P2 text and Advertise route.
- `POST /api/sponsorship/reports` accepts a current server-eligible campaign/creative pair, one of five reasons, and up to 300 characters. It has streamed 2 KiB body protection, origin and JSON checks, a five/hour trusted-IP limiter, bounded duplicate suppression, prepared SQLite writes, and a durable 201-only success contract. No login or private report-read API is required. The operator-only `sponsorship-reports-cli.ts` lists, views, reviews, and resolves reports; P3's existing campaign pause and creative disable commands remain the moderation actions. The in-memory abuse limiter resets after process restart and should be reviewed before any public commercial launch.

## P4 final performance closure (2026-10-29)

The exact uncommitted P3-only client build was not archived; commit `95a6787` predates P0–P4. Git worktrees, reflog/stashes, P3/P4 reports, and available local source did not provide a verifiable P3 snapshot. An isolated temporary **P4-off control** was built from the current P0–P4 source, changing only the Hub sponsor click path back to Advertise and making the P4 Hub catalog refresh a no-op. All other client source, assets, dependencies, P4 server code, local SQLite fixture, and production-build settings were identical. This isolates the runtime work added to the Hub by P4. It does not measure the exact historical P3 bundle or total cost of P4 routes outside the Hub.

Chrome 156.0.8078.48 on the same Mac and browser profile used the same-host `127.0.0.1:8093` production build, device pixel ratio 1, identical viewport/settings, a 10-second warm-up, then three independent 60-second observations per full scenario. Each sample reloaded the Hub with the browser cache disabled for a matched transfer condition. A `PerformanceObserver` counted long tasks; Chrome DevTools Protocol recorded network transfers and JavaScript heap. The frame metric is the **requestAnimationFrame interval** (presentation cadence), not CPU/GPU render time. Store and Advertise durations were measured from control activation to the relevant page appearing, then from Back activation to the Hub appearing. [Raw browser records](advertising-p4-evidence/performance-raw.json) retain all samples, including a separate 667×375 sanity run.

All full observations averaged approximately 60 displayed callbacks/second and recorded **zero long tasks** and **zero steady-state network requests**. The local demo image added 1,784 transferred bytes beyond P4 house state; its small size is fixture-specific and does not establish a future commercial image budget. The 60-second sponsored observations include the designed expiry-to-house transition; an additional browser check confirmed sponsored at load and house after 61 seconds. Restarting the same fixture server with global pause enabled returned `hub: null`, zero directory entries, and the house banner. Thirty Store → Hub cycles issued exactly one catalog request per return, no repeated image transfer with normal browser caching, and garbage-collected JS heap samples of 4.44, 4.51, and 4.52 MiB after each ten-cycle batch. No accumulating listener/timer or image-request pattern was observed. A 667×375 sponsored sanity run (20 seconds) had 16.7 ms p95 cadence and zero long tasks.

The browser's headless rAF cadence is capped at the display interval and does not prove exact GPU frame cost. Process/GPU memory and frame rendering time were unavailable from this measurement path. One compact Advertise opening took 697 ms; the other two were 208 and 212 ms, against control runs of 206–212 ms, so that isolated run did not repeat. There was no P4-specific source correction: the matched Hub measurements showed no material regression. The isolated QA server and browser were stopped, and its fixture was removed; the separate `qa` worktree and all P0–P4 source changes remained untouched.
